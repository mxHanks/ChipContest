# S3-Y32：4000 task/s 高并行架构的一手资料与解析边界

2026-11-10。本文只做资料研究与整数预算计算；未修改 RTL，未启动仿真、综合或 STA。既有“2026-11-09 上海时间 23:59 停止新增实验”的期限已过，本文不将该期限解释为继续实验的授权。

**面积约束更新：用户已明确本轮按比赛 2.25 mm² 上限，允许超过原 1.25 倍；当前主路线为复用型 8×8 共 64 PE＋真实 64 位搬运，4×16 备选。旧 25% 复制模型仅作历史比较，不再作为本轮淘汰条件。最终面积仍需核实库物理单位、官方 SRAM 计价和新增接口范围。**

**结论：64 个完整 INT16 MAC 有足够的理论算力，但只扩 PE 不能达到 4000 task/s。现共享 32 位通道的事务数已经超过每任务 37,500 拍预算；需同时改造搬运/端点吞吐，并保留真实清零和独立参数装载。推荐优先评估 8 行×8 列，4 行×16 列作为同条件对照。4000 是待验证目标，本文没有复现或证明截图中的 4509 task/s。**

## 固定口径与当前证据

保持每任务 `X[99][64] × W[64][256] + bias[256]`，X/W 为 signed16，bias 为 signed40，原 signed48 累加及最终 `RNE(acc/512)` 的 Y32 逐位语义。99 行共 25,344 个输出、1,622,016 次 MAC。每个任务重新装载自己的 W/bias，并对实际参数存储、X、ACC、结果/FIFO/快照执行真实物理清零；同任务内跨行复用 W 合法，跨任务保留参数不纳入方案。

现两行×八列候选完整 12 任务为 1,514,236 拍，含真实 clear 24,624 拍；按 150 MHz 换算为 1188.718 task/s。150 MHz 尚无完整 STA PASS，不能称为已实现频率。来源：[开发完整结果](s3-y32-dma-day-results.md)、[服务器综合边界](s3-y32-dma-server-synth-results.md)。

目标 4000 task/s 对应每任务 **37,500 拍**、12 任务 **450,000 拍**，要求 43.25376 次有用 MAC/拍。此预算含原主口径真实 clear；clear 后 gap 应继续单列并同时报告含 gap 吞吐。

## 先排除搬运的硬下界

现公开 ABI 与 DMA 逐任务事务数如下，均为共享通道上的 32 位请求。X 虽是 INT16，当前仍占一个 32 位源槽；bias 为 64 位源槽，不能误按裸 40 位流量计算。来源：[实际 DMA 接口说明](../experiments/s3-y32-dma-day/README.md)。

| 流量 | 当前事务/任务 | 仅将 X 改为 packed16 后 |
| --- | ---: | ---: |
| W 源读 | 8192 | 8192 |
| bias 源读 | 512 | 512 |
| X 源读 | 6336 | 3168 |
| Y32 写 | 25344 | 25344 |
| 合计 | **40384** | **37216** |

以下均为本文按上述事务数推导的乐观上界，不是新测量：

- 当前共享端点即便达到每拍一笔，40,384 拍仍大于 37,500，未计计算、清零和控制。增加 outstanding 或 FIFO 无法突破这个总服务量下界。
- 当前已测端点每 7 拍阻塞 1 拍。若保留该服务率，当前 ABI 仅总线下界即为 47,114.7 拍，吞吐至多 3183.72 task/s；packed16 X 后仍为 43,418.7 拍，至多 3454.74 task/s。
- packed16 X 配完美每拍一笔，单搬运已经消耗目标窗口的 99.24%；顺序执行现 2052 拍真实 clear 后至少 39,268 拍。不能靠隐藏 clear 的计时或跨任务复用声称达标。
- 例：若改为真正端到端 64 位搬运，W、X 均 packed16，bias 仍 64 位槽、Y32 相邻两列成对写，理想总量为 18,608 个 64 位 beat；按 6/7 服务率为 21,709.3 拍。此时才有合理重叠余量。仅把 DMA 内部寄存器加宽、末端仍串行成两笔 32 位请求，不具有该带宽。

可选路线是更宽共享端口，或物理独立的读/写银行与端口。两者都必须核算原端点和仲裁的实际接受率、SRAM 端口冲突、CPU 争用与写响应；不能将 AXI 的独立通道能力直接套到当前 ICB 单通道。

## 两个 64 PE 方案的真实差别

假定每 PE 每拍执行一个完整 signed16×signed16 MAC，K=64 连续无停顿；下表不含 INIT、偏置准备、流水首尾、RNE、排队、搬运和 clear。

| 项目 | 8 行×8 列 | 4 行×16 列 |
| --- | ---: | ---: |
| 行 tile 数（99 行向上取整） | 13 | 25 |
| 每行 tile 的列组数 | 32 | 16 |
| 纯 MAC 拍 | **26624** | **25600** |
| 尾行后的有用 PE 利用率 | 95.1923% | 99.0000% |
| 每拍 X / W 标量读取数 | 8 / 8 | 4 / 16 |
| W 的 INT16 片内读取总数 | **212992** | **409600** |
| 两套完整 X tile 缓冲 | 2048 B | 1024 B |
| 37,500 拍减纯 MAC 的余量 | 10876 | 11900 |

这些数字来自 `ceil(99/R) × (256/C) × 64`；最后 tile 只使能 3 行，禁止无效行输出。偏置按列广播给同 tile 各行，不为每行复制 bias SRAM。每个输出的 K 维归约和最终 RNE 位置保持原样。

**从权重复用角度优先 8×8。** 它保留现 8 路 W 读取形状，权重广播给 8 行，片内 W 读取仅为 4×16 的 52%；代价是更多 X 银行、广播扇出及尾行空槽。4×16 纯计算节省 1024 拍，但 W 读带宽加倍，作为主方案不足时的备选。现行上限为 2.25 mm²，无需为旧 25% 约束先强制重构全部存储/算术；这一偏好不代表任何一种已通过面积。此比较是本项目推断，不是文献替本设计做出的性能结论。

两者均只需一份 32 KiB W：现 8 列银行映射为 `bank=c mod 8, addr=floor(c/8)*64+k`，每 bank 深 2048，仍由两颗 1024×16 宏组成；16 列映射可用 `bank=c mod 16, addr=floor(c/16)*64+k`，每 bank 一颗 1024×16 宏。总宏数可保持 16，但 16 路读所需布线、写入分发及控制须重新实现。容量相同不等于面积或时序相同。

现有 native 映射中每 PE 约 2018.7006 库面积单位；原样新增 48 PE 的复制估算为 96897.6288，超过旧增量预算 65661.86935950，尚未计 X、结果和新接口。它是原结构复制模型，不是所有紧凑实现的面积下界。主计划中 engine＋X 的 8×8 复制模型为 478823.762238 库单位，**仅当单位为 µm² 时**相当于约 0.479 mm²、占新上限 21.3%；该模型仍缺新接口等完整费用，不能把条件换算说成面积通过。详见 [完整计划](s3-y32-4k-plan.md)。

X 必须分成 R 个同时可读银行；ping-pong 两套使下一 tile 装载与当前 tile 计算使用不同物理存储。单颗 1RW SRAM 的“地址不同”不产生两个读写口。以 tile 保存 64 个 raw48 结果需 384 B；若采用两槽整 tile 缓冲则为 768 B，也可流式分组保存，但必须证明最大生产突发与消费者停顿下不会覆盖结果。单路每拍一个 Y32 的 RNE 理论上可承受目标平均 0.67584 输出/拍；实际首尾与背压余量仍需计算。

## 一手资料支持的设计原则

1. **复用应同时考虑 X、W 和部分和。** Eyeriss 原论文讨论局部存储、PE 间共享与输出驻留等数据流，并说明高并行计算可能被带宽限制。这里借鉴“W 跨行广播、X 跨列广播、每输出部分和留在本 PE”，不直接照搬其卷积 row-stationary 映射，更不移用论文吞吐或节能倍数。[MIT 作者原论文，ISCA 2016，II、III-B、IV-B 节](https://www.rle.mit.edu/eems/wp-content/uploads/2016/04/eyeriss_isca_2016.pdf)

2. **装载、计算、写回解耦，并显式管理依赖。** Gemmini 官方实现将 load/store/execute 分为独立控制器，使用 banked scratchpad、访问队列/ROB；其大矩阵循环控制器对 tile 做双缓冲以重叠数据搬运和计算。对本项目可使用三个轻量控制器及明确槽所有权，不需要引入整个 Gemmini ISA/ROB。[Berkeley Gemmini 官方 README：Major Components、Matmul and Conv Loop Unrollers](https://github.com/ucb-bar/gemmini/blob/master/README.md#major-components)

3. **多在途隐藏延迟，需要实际缓冲。** AMD 官方说明 pipelined outstanding 请求可隐藏存储延迟，同时增加队列/存储开销。对本设计应先按端点延迟和所需速率推导 2/4/8 等队列深度，再以冻结事务流判断收益；不能承诺队列越深越快，更不能突破前述带宽下界。[AMD UG1399：AXI4 burst 与 outstanding 参数](https://docs.amd.com/r/en-US/ug1399-vitis-hls/Options-for-Controlling-AXI4-Burst-Behavior)

4. **响应归属和顺序属于设计的一部分。** AXI 官方 IP 文档明确同 transaction thread 有序、不同 thread 可能乱序。本项目 ICB 若保持有序，可用有限深请求归属 FIFO；若引入 tag/多端口，应加入任务、方向、地址/槽身份管理。首次错误后停止新发、排空已接受事务及仍保持 VALID 的承诺请求；所有 Y 响应退休且所有权为空后才完成。多在途会放大“错误被观察前已有后续写被接受”的范围，应明确保留部分写失败合同，不能声称还能撤销已接受写。[AMD PG059：Use of ID Signals](https://docs.amd.com/r/en-US/pg059-axi-interconnect/Use-of-ID-Signals)

## signed16 packed MAC 的特定限制

**packed16 存储/搬运可以保持位精确；不能由此推导一个普通乘法器能在一拍完成两个任意 full signed16 乘积。**

对独立两路，直接相乘 `(a0+2^s*a1)*(b0+2^s*b1)` 会产生 `a0*b1+a1*b0` 交叉项；对共享 W 的两路，两个完整 32 位乘积仍需足够的隔离位、符号扩展与进位修正。未经完整域证明，不能通过紧挨拼接得到精确双路结果。

AMD DSP48E2 实际是 27×18 signed 乘法器；`TWO24/FOUR12` 是加法器的 SIMD 模式，官方明确该模式必须禁用乘法器，不能当作“两路 INT16 乘法”。[AMD UG579，DSP48E2 Functionality、SIMD](https://docs.amd.com/api/khub/documents/pTysoma4TYgNH95BrY1Sbw/content)、[AMD 原语属性表](https://docs.amd.com/r/en-US/ug1704-spartan-ultrascaleplus-libraries/DSP48E2)

本项目是 S40 标准单元 ASIC，不以 FPGA DSP 数作为资源证明。可研究共享 W 的部分积逻辑复用，但必须证明所有 signed16 端点、符号、任意 K 前缀及最终 RNE 都与原模型一致，再由同库映射/STA 证明收益。INT8/INT4 打包、截断乘积、近似 MAC、稀疏跳过特定测试数据均不满足当前精确语义前提。

## 后续可执行评估顺序与结论等级

先冻结计时/精确语义与独立参数、真实 clear 合同；将共享通道带宽作为 go/no-go，再比较 8×8 与 4×16 的银行/缓冲/广播成本。后续若另获实验授权，按端点搬运→实际 MAC tile→真实 CPU 单任务→完整 12 任务逐步验证，最后使用同源同库面积与完整 150 MHz setup/hold、DRC、时钟覆盖判断是否可交付。新增 X/队列/快照也必须从公开口写脏后逐物理位置确认清零，不能沿用旧核心 clear 拍数作为新架构证明。

当前能够确定的是：**算力上 64 PE 可行；原 32 位共享端点条件下 4000 不可行；端到端扩带宽并良好重叠后 4000 有预算空间，但未取得实现、面积、时序或正式成绩证据。** 不同任务定义、量化位宽、时钟、参数驻留、清零计时或只量 compute 的 4509 task/s 截图，均不能据此作为本任务的同条件对照。
