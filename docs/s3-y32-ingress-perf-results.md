已完成本机功能和性能验证。保持原 CPU/LSU/BIU、原 mem_fab 源码与参数、32 位共享端点、64 PE 和全部数值/存储配置，完整 12 任务从 **504.3868 提高到 1064.3506 tasks/s**，吞吐为基线 **2.1102 倍**，总周期减少 **52.6108%**。全部频率换算以 150 MHz 为假定，尚未完成该新配置的 STA/PPA 验收。

实现位于独立分支 `codex/s3-y32-ingress-perf-20261113`，工作树 `/home/mxhanks/.codex/worktrees/s3-y32-ingress-perf/ChipContest`。父基线为 `349b486`；冻结硬件基线为 `bde23ba`，优化硬件子提交为 `5470c5650f2d11d16e7c52cc96626d21030a3973`。旧冻结目录和其他并行验收工作未修改。本轮本地提交，不推送或合并其他分支。

## 改动与边界

生产 RTL 只改两个文件：

- `xu_systembus_ingress32.v`：现有平台 arb 实例的响应归属 FIFO 从 1 项改为 4 项，只存源 ID。原 fabric 命令/响应队列各 2 项、splitter 最多 1 笔在途的参数完全不动。
- `xu_matrix_dma_sysbus32.sv`：新增 4 项有序 kind/index 队列。响应按接受顺序退休；保留 W 两半拼接、bias 物理提交、X 双 set 所有权、Y 最后一项响应后释放、错误排空和 DONE 条件。已声明但受背压的锁定命令在出错后仍完成握手并排空。

`verify_sources.py` 验证全部 168 个生产 RTL 文件集合及内容，除这两个文件外完全等于冻结子提交；CPU C/start/linker 源码也保持逐字节一致。X 仍为每 32 位槽一个 INT16，本轮没有实现 packed16-X，也没有改变输出位宽。

验证环境只把 source loader 从逐笔等响应改为最多 4 笔有序提交。每个任务先完成物理 clear，随后真实传输全部 15,040 个源写，等所有写响应退休后通知 CPU 启动。计时仍从 clear 请求至最后 Y 响应，包含全部加载、等待、控制与计算。poison 和验证读回仍在窗外，与 504 基线一致。

此结果对应此前 504 基线使用的原 SystemBus 三源加载刺激环境。新 GPIO→CPU 生产加载方案必须用优化后的同一 RTL 重新计时，不能直接套用 1064.35。CPU 开发仿真使用 289 个功能 RAMSP 模型及既有 CPU 行为 RAM；不将其称为 353 宏门级活动或功耗证据。

## 验证结果

- 原 fabric 饱和测试：1000 请求接收跨度 **3997→1997 拍**，全响应退休跨度 **4000→2002 拍**。原 fabric 的约两拍一笔能力已利用；生产双源与测试三源均通过四槽满、同时入出、环绕、归属、错误、背压、稳定命令与共同复位测试。
- 完整 CPU 12 层：304,128 个 Y32 精确一致，所有源装载、DMA、端点请求/响应独立守恒。实际 DMA 与连续 loader 峰值在途为 3，容量为 4；端点仍最多 1 笔。
- 同一 CPU 二进制首 DMA 端点额外等待 31 拍：总 140,968 拍；首 source 加载端点额外等待 31 拍：总 140,963 拍。等待完整进入测量窗口，其他相位变化不被误当作注入恰好只增加 31 拍。
- 独立 DMA＋实际入口＋原 fabric 功能模型：完整 12 层、背压、单行模式、末个 Y 响应已 VALID 后真实背压 97 拍全部通过。
- 三阶段复位后换参数恢复：76,032 个 Y32 精确一致；被复位取消的请求队列深度分别为 2、3、3。
- W 低/高、bias 低/高、X、首 Y、末 Y 七个指定地址错误后，各执行不同参数的完整任务：177,408 个恢复输出精确一致，无自动重试或早 DONE。
- 检查器负例：漏源写、漏 Y 响应、5 项在途、少一个物理清零写均被拒绝。

初次 CPU 构建遗漏了原物理 SRAM adapter，补上与冻结基线相同的 adapter 后重新构建；没有以移除观察器解决。初次 DMA 回归连接/编译参数错误，以及要求一定达到 4 项的过严测试均保留失败输出。后者由独立每拍台账、实际多项在途证明与入口满 4 回归替代。最终硬件源码未因这些测试修正改变。

## 为什么实测没有达到表中 1341

1341 tasks/s 是每笔恰好两拍、没有端点额外背压时的数据搬运理想边界。当前冻结共享端点模型每 7 拍禁受理 1 拍，保留该模型的隔离测试为 1000 笔 2335 拍，稳态约 **7/3 拍每笔**。现布局完整任务仍有 55,424 次共享端点传输；按该服务率再加现清零，乐观边界约 **1150.74 tasks/s**。实测还包含 CPU 共享邮箱轮询和计算/结果组切换等间隙，为该带宽估算的约 92.5%。这些服务率是开发模型的行为，不能直接当成物理 SRAM 时序。

因此本轮已实现所选的入口流水方向，并测得完整任务收益；1341/1512 两列的理想值不是实际性能承诺。不得通过排除源装载、取消端点背压、扩大总线或修改原 fabric 在途配置来追平该数值。
