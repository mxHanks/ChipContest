# B41 完整数据搬运吞吐可行性评估（Python RTL 级周期模型）

## 结论

此前只计算 DMA 读取和 Y 写回，漏掉了任务开始前把 X/W/bias 写入共享 SRAM 的 15,040 笔传输。本轮把完整闭环纳入：

```text
CPU/入口装载 -> 共享 SRAM -> DMA 重读 -> 计算与 Y 写回 -> 清零
```

冻结版的完整 12 任务日志（304,128 个 Y32 逐位一致）按用户提供的阶段汇总校准后，平均每任务约 **297,391 周期**，150 MHz 条件吞吐约 **504.39 task/s**。

| 阶段 | 周期/任务 | 占比 |
| --- | ---: | ---: |
| 源数据装载到共享 SRAM | 126,331 | 42.48% |
| DMA 读取、计算和 Y 写回 | 169,965 | 57.15% |
| 清零 | 1,028 | 0.35% |
| 其他/边界残差 | 67 | 0.02% |
| 合计 | **297,391** | 100% |

清零只有约 0.35%，主要瓶颈是共享 SRAM 入口和数据搬运。

## 完整事务账本

当前布局按 32-bit beat 计算：

| 数据段 | 写入共享 SRAM | DMA 重读/写回 | 事务数 | 数据量 |
| --- | ---: | ---: | ---: | ---: |
| X | 6,336 | 6,336 | 12,672 | 50,688 B |
| W | 8,192 | 8,192 | 16,384 | 65,536 B |
| bias | 512 | 512 | 1,024 | 4,096 B |
| Y | — | 写回 25,344 | 25,344 | 101,376 B |
| 合计 | 15,040 | 40,384 | **55,424** | **221,696 B** |

之前的 40,384 笔只包含：

```text
15,040 笔 DMA 重读 + 25,344 笔 Y 写回
```

完整任务还必须加上：

```text
15,040 笔 CPU/入口装载
```

因此，40,384 笔本身不能代表完整任务。完整 55,424 笔在理想每拍一笔、暂不计清零时是约 **2,706 task/s**；把当前 1,028 拍清零也计入后，理论上限约 **2,657.6 task/s**。

## Python 周期模型

模型脚本：[`tools/analysis/throughput_feasibility.py`](../../../tools/analysis/throughput_feasibility.py)

模型使用一个有序原互连服务器：每笔 32-bit 请求/响应事务占用固定 `service_interval` 个周期，依次处理源装载、DMA 重读、Y 写回和清零；残余项单独表示 CPU 邮箱、计算等待和其他控制开销。

运行命令：

```bash
python3 -B tools/analysis/throughput_feasibility.py \
  --out docs/validation/throughput-feasibility-r2/result.json
```

模型输出位于 [`result.json`](result.json)。它不修改冻结 RTL 或固件，也不宣称替代 VCS、门级仿真或 STA。

## 交通下限和隔离边界

| 条件 | X 布局 | 服务间隔 | 任务周期下限（含 1,028 周期清零） | 150 MHz 条件吞吐 |
| --- | --- | ---: | ---: | ---: |
| 理想一拍一笔 | 当前 X | 1 拍/笔 | 56,452 | **2,657.12 task/s** |
| 理想一拍一笔 | X packed16 | 1 拍/笔 | 50,116 | **2,993.06 task/s** |
| 冻结入口 + 原互连 | 当前 X | 4 拍/笔 | 222,724 | **673.48 task/s** |
| 优化入口 + 原互连 | 当前 X | 2 拍/笔 | 111,876 | **1,340.77 task/s** |
| 冻结入口 + 原互连 | X packed16 | 4 拍/笔 | 197,380 | **759.96 task/s** |
| 优化入口 + 原互连 | X packed16 | 2 拍/笔 | 99,204 | **1,512.04 task/s** |

这些是**仅考虑完整数据搬运和清零的乐观上限**，没有额外加入计算等待、软件轮询和异常响应延迟。它们与冻结版 504.39 task/s 的方向一致：当前真实入口和共享 SRAM 服务率是第一瓶颈。

## 把现有非搬运开销加回去

在 4 拍/笔的交通基线下：

- DMA 读取 + Y 写回交通成本：`(15,040 + 25,344) × 4 = 161,536` 周期；
- 当前观测的 DMA/计算/写回阶段为 169,965 周期；
- 推出的该阶段残余为 **8,429 周期**；
- 相对完整 4 拍交通下限 222,724 周期，冻结实测还多出 **74,667 周期**，其中包含入口等待、软件控制、计算等待、仲裁和边界残差。

如果把这部分已观测的非搬运开销原样加回，2 拍/笔并不能达到 1,341 task/s 的交通理想值；它只说明“服务率提升”本身的上限，不能当作已实现成绩。`result.json` 同时保存了交通理想值和加回残余开销的敏感性结果。

## 目标吞吐所需服务率

150 MHz 下的每任务周期预算为 `150,000,000 / target_tasks_per_s`。仅考虑清零、不留其他开销时，原互连所需平均服务间隔约为：

| 目标 | 当前 X 布局 | X packed16 |
| ---: | ---: | ---: |
| 1,000 task/s | 2.687 拍/笔 | 3.034 拍/笔 |
| 1,500 task/s | 1.786 拍/笔 | 2.017 拍/笔 |
| 2,000 task/s | 1.337 拍/笔 | 1.513 拍/笔 |
| 2,706 task/s | 0.883 拍/笔 | 0.998 拍/笔 |
| 3,000 task/s | 0.798 拍/笔 | 0.902 拍/笔 |

这说明：

1. 当前原互连约 2 拍/笔时，完整任务上限约 1,341 task/s；
2. X packed16 只能把 1,341 提高到约 1,512 task/s，不能单独冲到 3,000；
3. 2,706 task/s 要求当前布局达到小于 1 拍/笔的平均服务率，packed16 也几乎需要 1 拍/笔，而且没有余量给计算和控制；
4. 因此在保持官方原互连、32-bit 接口、完整装载和完整 Y 写回的条件下，当前证据不支持 3,000 task/s 承诺。

## 推荐验证顺序

1. **CPU 邮箱轮询退避**：保持总数据量不变，只减少入口空转，确认 126,331 周期中的软件等待比例。
2. **连续装载**：在原 32-bit System Bus 上保持请求连续，不增加宽度、不加旁路，测量服务间隔是否从 4 拍接近 2 拍。
3. **X packed16**：只改 X 的可复现布局和地址映射，重新生成脚本、向量、golden 和 RTL 断言；预计每任务减少 6,336 笔事务。
4. **入口请求流水**：在原互连允许的范围内优化请求锁定、响应退休和 DMA/CPU 仲裁。
5. **结果批次间隙**：测量完整 Y 写回之间的空洞；不能使用独立写口或 direct stream 填补。
6. 每一步都重新跑单任务、12 任务、600 样本精度、四态/门级和同一计时口径，不能只看局部吞吐。

## 官方合规边界

本评估没有引入 64-bit/128-bit 总线、压缩输出、共享 SRAM 旁路、TB 预加载或独立结果写口。所有优化候选仍需满足：原 System Bus、32-bit 接口、完整参数加载计时、完整 99×256 输出、唯一冻结配置以及官方 150 MHz/面积/功耗/精度验收。

本报告是诊断测量和理论边界分析，不是正式比赛成绩。
