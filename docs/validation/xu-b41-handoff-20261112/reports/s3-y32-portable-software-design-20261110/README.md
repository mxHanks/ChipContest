## 已实现

- `software/ffn_wait.h`：统一等待逻辑，支持紧轮询、固定间隔、先快速读取再固定等待、先快速读取再有上限退避。没有跨任务在线学习。
- `software/rv32_port.h`：静态 RV32 适配，访问状态、mcycle、错误码及 NOP 块。完成后的 fence 由调用方保留；错误码发布包含 fence。
- `software/reference_driver.c`：参考清空、地址配置、启动、等待、上报流程。硬件清空和每任务重载保留，未引入任务队列、WFI 或提前完成。
- `tools/run_validation.py`：实际 C 控制测试、有限合成时延筛选和 O2/O3/Os 的真实 RV32 构建；每份参考固件使用生成的固定配置。

通用代码不按 PE 数量直接调度 MAC，也不推断新版硬件的寄存器、Bank 或数据布局。`group_y_reference.h` 是已知旧接口的示例，不能直接标成新版 64 PE 配置。

## 验证结果

最终回执：[RESULT.json](RESULT.json)。原始结果在 `results/validation-r2/`。

| 验证 | 结果 | 实际范围 |
|---|---|---|
| 实际 C 等待逻辑 | 72 项通过 | 四类策略，错误优先、BUSY/DONE、CLEAR、立即完成、迟到完成、32 位回绕、超时、轮询上限、背靠背调用及暂停上限 |
| 单变量负控 | 3 项均被检出 | 忽略 BUSY、DONE 时跳过 ERROR、错误接受超时 DONE |
| 合成控制场景 | 15 配置 × 156 场景，共 2,340 项通过 | 显式假设的时延和端口成本模型，不是 CPU/RTL 仿真 |
| RV32 固件构建 | 15 配置 × O2/O3/Os，共 45 份通过 | GCC15.2，RV32IMAC；检查实际反汇编、栈、内存段、fence、无 WFI 和固定完成符号 |
| 真正 64 PE 的严格 CPU／RTL | 控制及两主线完整开发验证通过 | 同一 `a80dd18` RTL，CPU SVA 开启；full12／错误／背压／CPU-only活动原件重算通过 |
| B 版综合、面积和 STA | 部分完成 | 已获原生综合及独立 SS/FF 四场景回读。setup 无负裕量，hold 仍有违例。三份软件的门级验证和物理能量待做 |

控制测试直接调用实际 `ffn_wait()`，受控适配替换状态、时钟、错误发布和暂停原语。它不能证明硬件内存屏障顺序或真实 MMIO 的最坏响应时间。

新的等待逻辑在每次状态读取返回后核对时间预算，ERROR 优先于超时及 DONE，超过预算才观察到的 DONE 返回超时。这个期限语义比旧固定 NOP 补丁更明确，也与旧补丁不同；当前候选不能沿用旧 RTL 的通过结论。

时间预算和轮询次数均有限，但被阻塞的 MMIO 或一段暂停可能先越过预算，再在下一次检查被发现。它不是独立硬件 watchdog。32 位无符号时间差要求预算及相邻观测间隔小于 2³¹ 拍；真实适配须确认这些前提。

## 实际做出的编译优化

第一版通用实现中，GCC 在 O2/Os 下可能保留整套等待参数分支和全部 NOP 块。最终版明确让固定策略展开，并按配置上限裁掉 NOP 分支，避免通用化引入额外代码。

下表比较**本次新通用实现专门化前后**，不是相对生产固件的加速或能耗收益。`text` 含参考启动代码和只读内容。

| 配置 | 初版 O2 text/字节 | 最终 O2 text/字节 |
|---|---:|---:|
| 紧轮询 | 5,584 | 546 |
| 固定 64 NOP | 5,584 | 650 |
| 固定 256 NOP | 5,584 | 1,038 |
| 快速读取后固定 64 NOP | 5,584 | 664 |
| 8→256 NOP 有上限退避 | 5,584 | 1,628 |

作为体积参考，旧 GCC15/O2 固件的紧轮询、64 NOP、256 NOP 分别为 492、656、1,042 字节。新旧超时检查和实现不同，这些字节数只能用于评估通用框架体积，不能据此判断运行时间或省电比例。

最终版 O2 的固定 64/256 NOP 参考构建中，`main` 静态栈为 16 字节；启动仍定义 s0–s11，完成符号仍位于 `0x80000086`，`.data/.bss` 均为零。完整 45 份信息见 `results/validation-r2/cross/result.json`；编译成功没有替代真实 CPU 回归。

## 模型给出的取舍

模型仅对状态读取、计时器读取和 NOP 暂停收费。状态/计时器操作成本、每个 NOP 的成本及完成时刻均为公开列出的假设；C 分支和算术、真实取指、总线波形、SRAM 活动与库功耗未建模。单位为模型 tick，不是实测 E203 周期。

相同 156 场景的示例结果：

| 策略 | 状态读取总次数 | 相对紧轮询 | 最差完成发现延迟/模型 tick |
|---|---:|---:|---:|
| 紧轮询 | 226,030 | 0% | 72 |
| 固定 64 | 26,176 | −88.42% | 196 |
| 固定 256 | 8,038 | −96.44% | 580 |
| 快速读取后固定 64 | 26,536 | −88.26% | 188 |
| 8→256 有上限退避 | 8,800 | −96.11% | 564 |

这说明“读取少”与“完成发现及时”存在取舍；分阶段策略也不保证对所有相位都更好。候选集没有依据这些模型自动选择生产配置，更没有以任意权重把访问次数换算为能量或官方分数。

## 如何复跑和使用

从项目根目录运行，输出目录必须是新目录：

```sh
python3 -B reports/s3-y32-portable-software-design-20261110/tools/run_validation.py \
  --out reports/s3-y32-portable-software-design-20261110/results/new-run \
  --cross-prefix /tmp/xu-riscv-toolchain/bin/riscv-none-elf-
```

也可将本目录复制到其他位置，脚本使用随附的源文件和参考启动文件；本机编译器及 RISC-V 交叉编译器需要可用。

每份交叉构建目录的 `selected_config.h` 在编译时固定策略，包含参考预算，不代表已经标定的 64 PE 参数。默认完整流程同时保留紧轮询控制组。输入清单、命令、编译器、ELF/映像 SHA、反汇编和模型逐项 CSV 均保留。
