# 64 PE 并行开发中的通用软件优化

状态：本文保留第一阶段的设计依据；第二阶段已取得主 `d60e0e0`／子 `a80dd18` 的真实64 PE方案并开展 CPU／RTL 验证。当前进度与结果以 README.md、PROGRESS.md 和 hardware64-r1/CPU64-RESULTS.md 为准。用户确认采用离线测量和搜索、正式运行固定配置；运行时学习留作后续候选。下文“待取得64 PE方案”描述的是第一阶段结束时的依赖，已由第二阶段解除，不能作为当前状态。

## 已明确的范围

- 现在的成果应是可复用的驱动策略、固件优化方法、验证夹具和硬件版本配置接口。
- 当前以源码复用为设计基础；实际地址、模式、数值布局及等待参数由具体硬件适配。尚未承诺相同二进制无需配置即可适配任意硬件。
- 第一阶段沿用已有任务数值语义；输入格式、权重编码、PE 排布、Bank 映射、硬件队列和中断能力随未来硬件方案再定。
- 软件与硬件并行开发；本目录独立保存设计，不修改正在交付的硬件、主聊天报告或生产固件。
- 最终选择围绕官方得分比较吞吐与全 SoC 单任务能耗。代码体积、轮询次数、退休指令和 RTL 翻转用于解释结果，不能直接替代能量。

## 代码核对得到的边界

已读历史冻结 Group-y 的 `dma_day_main.c` 和 `xu_matrix_dma.sv`：驱动执行清空、设置 X/W/B/Y 四个基址、启动、等完成和上报。CPU 没有按 PE 数量直接执行 MAC 调度循环。硬件内部扩大 PE 数量，不必自动引起这个任务流程变化。

该历史寄存器接口只提供固定 ID 和状态/计数寄存器，没有 PE 数量或通用能力查询寄存器；BUSY 时配置地址写入会报错。由此不能假设新版存在任务队列、后台描述符更新、WFI 完成唤醒或运行中缓冲切换。这些事实仅绑定所读旧版本，64 PE 版本以用户之后提供的方案为准。

旧软件报告包含 0/64/256/1024 NOP 的全任务结果和 41 项实际 C 等待逻辑检查，可复用其测试方法与失败场景。具体等待参数、活动排名和能耗收益均须在新硬件重新验证。

## 第一阶段的工作包

### A. 可配置等待策略

保留紧轮询控制组，比较固定间隔、有限阶段切换和有上限退避。完成时长缩短、总线拥塞、立即完成及异常长任务均纳入覆盖，策略不能依赖“64 PE 恰好比 16 PE 快四倍”。

每个候选都要保留错误优先、BUSY 未结束时不得成功、错误码回传、完成后的可见性约定和有限等待。CLEAR 与计算完成可以使用不同策略。超时按明确的时间预算表达，并保留必要的轮询次数兜底；不把 NOP 条数当成整个循环的真实周期。

用户已确认先离线选择策略参数，并在正式构建中固定配置；阶段切换可以按预设规则执行。运行时不跨任务学习新参数。

### B. 提交、完成与取指热路径

对比 O2/O3/Os、必要的链接时优化、函数内联与代码布局；一次只改变有明确测量问题的因素。检查实际 RISC-V 反汇编、段大小、栈用量及启动/完成约定。

收益指标包括从开始配置到启动被接受的开销、硬件完成到软件发现/上报的延迟、MMIO 和计时器访问、ITCM 活动。当前驱动已很短，因此不预设能获得大幅吞吐提升。

任务固定常量和地址计算可在语义允许时提前准备，但不提前发布完成、不写正在被硬件消费的数据，也不把官方应计时的工作移出计时窗。内存屏障只有在后续硬件与总线顺序证明充分时才考虑改变。

### C. 最小的硬件适配边界

通用任务流程只依赖提交、状态、错误、清空和完成可见性这些操作。寄存器、模式位、内存布局和等待参数放在具体版本配置中。性能关键路径优先让编译器静态展开，避免为可移植性添加不必要的逐次间接调用。

第一版提供已知旧接口的参考适配；64 PE 配置保持待填。未证实的能力不能自动开启。每次构建记录所用硬件配置、源码和固件身份，避免把某个硬件的最佳参数套到另一版本。

### D. 可复用测量和选择入口

同一测试入口执行不同等待策略与构建选项，分别记录提交、计算、最终写回、完成发现和上报时间。保存逐任务值与总值，避免只看 DMA 最终写回而漏掉下一任务启动受软件上报拖延的情况。

CPU 仿真、受控 MMIO 模型与真实硬件测量分别标明范围。没有库和对应活动数据时，不用访问次数乘任意权重编造能耗分。正式能量取得后，才按相同竞争参照和逐项舍入计算评分差。

## 验证顺序

1. 复用已有实际 C 函数测试的结构，扩展覆盖完成时间、轮询相位、MMIO 响应延迟、ERROR/DONE/BUSY 组合、超时边界、计时器回绕和连续任务。测试应直接调用真实候选逻辑。
2. 交叉编译候选并检查实际指令、代码大小和栈；在明确的成本模型下做控制路径筛选。模型只能证明被建模的控制行为与取舍。
3. 对接真实 64 PE 方案后，用自有 Linux 的既有隔离与资源流程做真实 CPU/RTL 同条件对照。重型作业在硬件输入及工作区明确后安排。
4. 候选完成同任务定义的 full12、逐位输出、清空、跨任务退休与故障验证，再交付与该网表绑定的固件及活动输入。需要专业环境的门级和物理能耗阶段与队友协调。

目前没有收到并核实当前 64 PE 的 RTL/ABI/构建输入，因此不能给出 64 PE 周期、能耗或最优参数。已有 16 PE 结果是历史参考；模拟更短的完成时间也不能代替真正的 64 PE 回归。

## 收到硬件方案后的定向工作

按实际布局优化打包/装载；按缓冲所有权实现双缓冲；按真实描述符队列做批量提交；按真实中断连接评估 WFI；按 Bank、总线宽度与行列调度安排传输。只有硬件支持及官方任务边界明确后，才评估跨阶段或跨任务重叠。

## 已确认的策略选择

采用“离线标定、构建时固定策略配置”，将正式运行期间的在线学习留作后续独立候选。正式参数须从对应硬件的测量产生；合成时延场景只用于验证通用控制路径和筛选候选。

已在独立目录实现通用策略、受控模型测试和 RV32 参考构建。72 项实际 C 检查、3 个负控、2,340 个明确假设下的场景及 45 份 RV32 参考构建通过。额外消除了 O2/Os 下无关等待分支的保留开销。对应硬件配置仍需等待真实方案；没有将合成模型中的某组参数选成生产参数。当前没有创建 ADR，因为这些选择仍易于逆转。
